## Findings

### WR-01 — A partial send failure can cause duplicate customer replies

Severity: Warning

Reference: [server/routes/inbox.js:125](../../server/routes/inbox.js#L125)

The route sends the email first, then marks the Gmail message handled, then persists `status: 'resolved'`. If either `markMessageHandled` or the Supabase update fails after Gmail accepts the send, the endpoint returns an error while the obligation remains sendable. The admin UI will invite a retry, which sends the same reply again.

Fix: make the send operation idempotent. At minimum, persist a `sending` state with an idempotency key before calling Gmail and persist the Gmail sent-message ID immediately after the send. Treat label removal as a separately retryable follow-up. On retry, detect the recorded sent-message ID and finish reconciliation without sending again.

### WR-02 — Inbox student context silently reports zero bookings and pieces

Severity: Warning

References: [server/utils/inboxProcessor.js:108](../../server/utils/inboxProcessor.js#L108), [server/utils/inboxProcessor.js:115](../../server/utils/inboxProcessor.js#L115)

The upcoming-bookings query filters `bookings.class_date`, but class dates live on the related `class_instances` row throughout this codebase. The pieces query filters `pottery_pieces.student_id`, while the extracted `piecesDb` and pottery routes use `customer_id`. Both queries discard their Supabase `error` values, so failures become `0` bookings and `[]` pieces. That false context is then given to the drafting model and may produce an incorrect customer reply.

Fix: join `bookings` to `class_instances!bookings_class_instance_id_fkey(class_date)` and filter/count future joined rows, filter pieces by `customer_id`, and check/throw or explicitly surface every query error before constructing the AI context.

### WR-03 — Account-anomaly links use an ID where the route requires an email

Severity: Warning

Reference: [frontend/src/pages/AdminDashboard.jsx:192](../../frontend/src/pages/AdminDashboard.jsx#L192)

The anomaly card links to `/admin/students/${a.student_id}`. The registered detail route is `students/:email`, and `AdminStudentDetail` passes that parameter to the email-based admin API. Clicking an anomaly therefore opens a numeric value as though it were an email and fails to load the affected student—the exact workflow this panel is intended to enable.

Fix: include `student_email` in each anomaly result and link with `encodeURIComponent(a.student_email)`, or add and use a dedicated ID-based student-detail route/API contract.

### WR-04 — A failed anomaly probe is presented as “All clear”

Severity: Warning

Reference: [frontend/src/pages/AdminDashboard.jsx:53](../../frontend/src/pages/AdminDashboard.jsx#L53)

Any network, authorization, or server error is converted to `setAnomalies([])`. The renderer interprets an empty array as a successful probe with no findings and displays “All clear.” This creates a false operational assurance precisely when the invariant check did not run.

Fix: model the request as separate loading/error/data states. Render “Unable to check” with retry/diagnostic affordance on failure, and reserve `[]` exclusively for a successful response containing no findings.

### WR-05 — Priority ordering is lexicographic, not urgency ordering

Severity: Warning

Reference: [server/routes/inbox.js:45](../../server/routes/inbox.js#L45)

Ordering the text values ascending produces `high`, `low`, `normal`, `urgent`, not `urgent`, `high`, `normal`, `low`. Because this ordering is applied before the 100-row limit, urgent obligations can be pushed below lower-priority messages or omitted from a busy inbox response.

Fix: store a numeric priority rank, expose a database view/RPC with a `CASE` ordering, or fetch bounded active rows and sort by an explicit rank map before applying the response limit.

### WR-06 — Calendar roster sync is abandoned after the HTTP response

Severity: Warning

References: [server/routes/classes.js:465](../../server/routes/classes.js#L465), [server/routes/classes.js:1053](../../server/routes/classes.js#L1053), [server/routes/classes.js:1119](../../server/routes/classes.js#L1119)

The new calendar updates are launched as unawaited promises and the handlers immediately send their responses. In the documented Vercel/serverless deployment, execution may be suspended once the response completes, so these Google Calendar writes are not guaranteed to finish. The multi-class handbuilding path also starts every sync concurrently without awaiting any of them.

Fix: await `syncClassInstance` before responding when calendar freshness is part of the operation, use `Promise.allSettled` for the handbuilding batch, or enqueue durable background work / register the promises with the platform's supported post-response lifecycle mechanism. Log failures rather than swallowing them with empty catches.
